FMEA - SOFTWARE FAILURE MODE EFFECT AND ANALYSIS 

PURPOSE 

Software Failure Mode and Effects Analysis (sFMEA) is a bottom-up method for identifying how a software function or component can fail, 
what effects result, and  what controls can prevent or detect it.

sFMEA is used by coding agent to reason about potential failures 

sFMEA does not establish that a failure exists. It produces failure hypotheses that should be verified against code, tests or other evidence

Scope:

Acceptance:
Observable conditions that would show the task is done. Establish them from the task text first, then from

VIEWPOINT MAPPING

Goal : Using sFMEA viewpoints identify potential failure modes within the function/component:

sFMEA viewpoints refers to the specific perspective or lens through which the dependency graph is analyzed.When reasoning about relevance to viewpoint
this helps guide reasoning
The following are sFMEA  dimensions:
- Functional viewpoint is relevant whenever the evaluation goal is verifying whenever a software component 
fufills its specified algorithmic and business rules, mathematical models  functional requirements 
Does this function correctly transform valid input X into expected output Y across all standard, boundary, and extreme domain conditions according to the specification?

software specific failure dimensions to associate with functional viewpoint: incorrect, unexpected

- Data viewpoint is relevant whenever the component reads, transforms, stores or passes values whose
shape, range, encoding or lifetime matters.
Can this function receive, hold or produce data that is malformed, missing, out of range, stale or inconsistent, and what happens to it?
software specific failure dimensions to associate with data viewpoint: incorrect, missing, corrupted, out of range, stale

- Control flow viewpoint is relevant whenever the outcome depends on branching, looping, ordering, error handling or concurrency.
Can this function take a path, order or number of iterations the specification did not intend, including skipped steps, unhandled errors and non termination?
software specific failure dimensions to associate with control flow viewpoint: skipped, wrong order, unhandled path, non terminating, timing

- Interface viewpoint is relevant whenever the component is called by or calls another function, module, process or user, so that a contract exists between the two.
Does each side agree on types, units, ordering, optionality, error signalling and timing of what is exchanged?
software specific failure dimensions to associate with interface viewpoint: mismatched contract, wrong type or unit, missing, extra, late

- Dependency viewpoint is relevant whenever the component relies on code, libraries, services, configuration or the environment that it does not control.
What happens when a dependency is absent, slow, changed, returns something unexpected or has side effects the component did not account for?
software specific failure dimensions to associate with dependency viewpoint: unavailable, incompatible, unexpected behaviour, side effect

- Security viewpoint is relevant whenever the component handles input from outside a trust boundary, or controls access to data, resources or capabilities.
Can an actor who should not be able to reach, alter, read or exhaust something do so through this function?
software specific failure dimensions to associate with security viewpoint: unauthorized access, injection, disclosure, tampering, exhaustion

For each component work through the question of every viewpoint that is relevant, and answer each one for that component.
A viewpoint that does not apply should be skipped, not forced.

Formulate each failure separately:
Under condition X, function Y fails to perform required behavior Z by exhibiting observable deviation D.


FAILURE MODE AND EFFECT 
For each failure formulated  map a software failure mode to a function or component/module: 

For each failure mode ask and reason about the effects of failure mode
If this failure occurs, what does it impact?

- Does it stay local?
- Does it propagate to callers?
- Does it corrupt shared state?
- Does it cause an exception?
- Is the exception handled?
- Does it cause a retry?
- Does retry amplify the failure?
- Does it affect another subsystem?

RPN / confidence assessment 
Using rpn scoring with severity and likelihood scoring 
Severity:
1 - Negligible : no observable effect on behaviour
2 - Minor : degraded or cosmetic, stays local, recoverable
3 - Moderate : wrong result for some inputs, reaches callers
4 - Serious : corrupts state or data, or is security relevant
5 - Catastrophic : effect propagation to sub system is high

Likelihood:
1 - Remote : no plausible path to the failure was found
2 - Unlikely : requires an unusual combination of conditions
3 - Possible : requires a plausible but uncommon condition
4 - Reasonably probable : arises under normal use or from a common mistake in this kind of code
5 - Frequent : failure mode surfaced in initial analysis and historical knowledge showed failure pattern

Confidence:
0 - not confident 
1 - confident

RPN = severity x likelihood. Treat a failure mode backed only by inference as lower confidence than one backed by repository code or retrieved history.

PREVENTIVE CONSTRAINT
For each failure mode state the constraint that would prevent it, written so that a coding agent can apply it while implementing,
and a check that would detect it if it happened anyway.
